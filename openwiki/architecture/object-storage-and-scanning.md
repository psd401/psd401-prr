# Object Storage, Quarantine, and Malware Scanning

Every file the system accepts, whether a staff upload, an intake email attachment, a Vault
export, or a generated production artifact, lands in private object storage first. Two
modules own that boundary. [`apps/secure_files.py`](../../apps/secure_files.py) is
deliberately domain-neutral: it knows about object keys, integrity metadata, and malware
scanning, not about requests. [`apps/records/storage.py`](../../apps/records/storage.py)
decides which keys a domain may use and stores immutable generated artifacts.

## Quarantine and promotion

Uploaded content is written under a quarantine prefix. The prefixes are listed in
`_QUARANTINE_KEY_PREFIXES` in `apps/secure_files.py`: intake, correspondence raw and
attachment storage, Vault messages, legacy files, and record uploads. The lifecycle is:

1. `store_quarantined_object` writes the bytes under a generated quarantine key.
2. `scan_object_for_malware` streams the object to ClamAV in chunks
   (`_clamav_scan`, one-megabyte chunks) and checks integrity while it reads, so a
   changed object cannot pass with a clean verdict.
3. A clean result leads to `copy_clean_object` or `promote_clean_object`, which moves the
   bytes out of quarantine. An infected or unscannable result keeps only the evidentiary
   metadata, and the bytes are removed with `delete_quarantined_object`, which lists every
   object version before deletion.
4. `open_private_object` is the only read path. Callers reach it after their own
   authorization checks, and it does not open a quarantined key for a download.

`AttachmentScanUnavailable` marks a file as not classifiable as clean. Callers must
refuse the file, not accept it. `apps/records/attachments.py` applies the same rule to
intake uploads: `validate_attachments` checks file signatures and archive structure
before anything is stored, and `scan_object_for_malware` is called on the stored object.

Scanner and storage health have their own probes: `probe_object_storage` makes one
read-only bucket request, and `probe_clamav` requires an exact `PONG` response within a
bounded time. Both feed the readiness checks in [operations](../operations/deployment.md).

## Multipart upload limits

Size and count limits run before any storage handler sees bytes.
[`apps/records/upload_handlers.py`](../../apps/records/upload_handlers.py) defines a shared
`_MultipartLimitUploadHandler` and two subclasses:

- `IntakeAttachmentLimitUploadHandler` enforces the `PRR_INTAKE_ATTACHMENT_*` count, per-file,
  and combined-size settings for files attached to a new request.
- `RecordUploadLimitUploadHandler` enforces the `PRR_RECORD_UPLOAD_*` settings for candidate
  records a Records Officer adds to a case.

The limits are read once per request, on the first file, so every chunk of an upload is judged
against the same values. A breach raises `StopUpload` and stores a refusal message on the
request. The public intake view (`apps/records/public_views.py`) and the staff request
upload path (`apps/api/resources/requests.py`) insert the matching handler into
`request.upload_handlers`. `apps/records/tests/test_intake_attachments.py` imports these
handlers directly for its limit checks. Limit values are app-managed settings
([configuration](configuration.md)), so change them through the settings registry, not in
the handler.

## Generated keys and immutable artifacts

`apps/records/storage.py` owns the key namespace for generated objects: record originals,
derivatives, productions, exemption logs, Vault exports, and Vault messages each have a
`generated_*_storage_key` helper. Keys are derived from request and record identifiers,
never from a filename. `_validate_generated_key` rejects keys outside that namespace.

`store_immutable_object` writes a generated artifact and records its size and SHA-256.
`load_verified_object` reads it back and fails when either value differs
(`_validate_integrity_facts`, `_digest_source`). Production packages and exemption logs
depend on that check, because a package that no longer matches its manifest must not be
released ([installments and release](../domain/installments-and-release.md)).

## Who depends on this

- Intake and correspondence attachments are scanned before a person can download them
  ([requests](../domain/requests.md), [correspondence](../domain/correspondence.md)).
- Record uploads and Vault ingest route each file through the same quarantine path
  ([case workspace](../domain/case-workspace.md), [collection and Vault](../domain/collection-and-vault.md)).
- Record review and handling read only verified bytes
  ([record review](../domain/record-review-and-handling.md)).

## Change guidance

- Add a new upload or generated-artifact path by choosing a generated key helper, or by
  adding a dedicated one in `storage.py`. Do not pass a display filename into a key.
- Any new quarantine namespace must be added to `_QUARANTINE_KEY_PREFIXES` so the
  storage-prefix grants cover it.
- Do not add a path that reads an object before its scan verdict is clean. The
  `open_private_object` boundary is the only supported read.
- Scanner and object-store configuration is a deployment concern. Do not hard-code
  endpoints, bucket names, or credentials in code or docs.

Focused tests: `apps/records/tests/test_record_storage.py` (generated keys and verified
reads), `apps/records/tests/test_storage_prefix_grants.py` (prefix grants),
`apps/records/tests/test_intake_attachments.py` (file signatures, archive limits, and
scan outcomes), and `apps/api/tests/test_record_uploads.py` (upload scanning and refusal).

Minimal validation: `PYTHON_DOTENV_DISABLED=1 python manage.py test apps.records.tests.test_record_storage apps.records.tests.test_intake_attachments --settings=config.test_settings`.
Run the MinIO-backed suites only when a change touches the object-store contract itself,
because they need the local object store.
