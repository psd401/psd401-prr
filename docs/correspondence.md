# Requester correspondence architecture

This document is the hand-written source of truth for requester correspondence.
Generated OpenWiki pages must not be edited by hand. The implementation lives
in `apps/correspondence`; request status and deadline effects remain in
`apps/records`.

## Ownership boundary

Django owns every decision and durable record that can affect the requester or
the district's legal position:

- drafts, deterministic rendering, approval, immutable content snapshots, and
  exact recipient snapshots;
- whether a message is legally eligible to queue;
- the delivery job, leases, retries, reconciliation state, and attempt history;
- inbound MIME parsing, attachment quarantine, deterministic matching,
  canonical bare-mailbox email intake, manual match corrections, and
  clarification-cycle state;
- request lifecycle effects through `apps.records.services.transition()`;
- staff permissions, audit entries, operational visibility, and REST
  capabilities.

Outbound transport is in-process. A Celery worker claims the same durable
delivery lease, builds RFC822 bytes from the frozen Django snapshot, opens only
clean released attachments through the existing claim-bound service, sends
through the mailbox-pinned Gmail client, and reports the result through the
existing delivery-result service. It runs as a migration-provisioned,
non-login system principal holding exactly
`correspondence.deliver_outbound_correspondence`.

Inbound transport is also in-process. A minute Celery poller reads a durable,
mailbox-and-environment-scoped Gmail history checkpoint, fetches `format=raw`
messages with authoritative Gmail metadata, and calls the same Django receiving
service that retains, parses, quarantines, scans, deduplicates, and matches the
evidence. Eligible plain unmatched mail then calls the shared records-intake
service; no integration-specific inbound submission, outbound claim/result, or
claim-bound attachment route remains.

## Domain records

| Record | Responsibility |
|---|---|
| `Correspondence` | One inbound or outbound communication. It carries draft content and structured metadata, immutable approved content and metadata, deterministic RFC Message-ID, opaque reply token, provider identifiers, actors, timestamps, failure category, optimistic version, and any resulting `StatusEvent`. |
| `CorrespondenceRecipient` | Exact To/Cc/Bcc address and display-name snapshot. It freezes when the parent leaves draft state. |
| `CorrespondenceDenialCitation` | One protected `ExemptionCitation` FK selected by an accountable Records Officer for a full-exemption denial, plus immutable citation wording and review-requirement snapshots. The set freezes at approval. Current taxonomy and second-review rules remain send-authorization gates; after a send claim, legal effects verify the immutable through rows against the approval digest so a taxonomy edit cannot erase genuine transport evidence. |
| `CorrespondenceDelivery` | The single transport job for an outbound message. Retries and reconciliation reuse this row and its Message-ID; they never create a replacement send identity. |
| `CorrespondenceDeliveryAttempt` | One lease/send/result attempt. It may be finalized once, then cannot be changed or deleted. |
| `CorrespondenceDeliveryNotification` | One append-only, privacy-minimized recipient outcome from an inbound RFC 3464 delivery-status notification. It links the retained inbound receipt to the stable outbound delivery without rewriting either delivery result or request state. |
| `InboundCorrespondenceReceipt` | Idempotent transport receipt and private raw-message evidence, including provider/RFC identifiers, parsing state, matching state/method, quarantine state, and any matched records. |
| `CorrespondenceAttachment` | Private inbound or outbound attachment metadata. Storage keys are generated by Django; filenames are display metadata only. |
| `InboundQuarantineWriteReservation` | Immutable, generation-numbered evidence committed before object storage I/O for every inbound raw message or attachment. It records the generated-key identity, expected size/digest, stored/adopted state, and leased cleanup attempts without putting object keys or requester PII in audit output. |
| `InboundQuarantineTransportAlias` | Immutable hashed idempotency/provider identity bound to one canonical raw-message identity. It preserves conflict detection across reservation generations and replacement inbound credentials without storing transport PII. |
| `ClarificationCycle` | The legal/application clarification state, separate from its messages. A deterministically matched reply, or a Records Officer's explicit association of an already-matched general message, can populate `responded_at`; association never resolves the request. Only an accountable human can resolve it. A human-attributed withdrawn or abandoned closure cancels the still-open cycle without inventing a response. |

`PublicRecordsRequest` remains the legal case record. Its original description
is never edited. `StatusEvent` and `AuditLog` remain the append-only legal and
operational histories.

## Lifecycles

Outbound correspondence follows:

```text
draft -> approved -> queued -> sent
                     |        ^
                     v        |
                  failed -> retryable/reclaimed
                     |
                     v
                 cancelled (only before a successful send)
```

The correspondence row records recipient-visible state. The separate delivery
row records `pending`, `claimed`, `awaiting_reconciliation`, `sent`, `failed`,
`retryable`, or `cancelled`. A lease expiry changes delivery eligibility, not
content or Message-ID.

Inbound correspondence follows:

```text
private raw receipt -> parsed -> matched received correspondence
                         |             |
                         |             +-> request conversation
                         +-> unmatched / ambiguous candidate / quarantined
```

A request number the requester wrote is a candidate only, never a match: the
subject is read first, and the body only when the subject names no number.
Two different numbers in whichever was read make the message ambiguous. Neither
placement silently attaches a message; a person confirms the case.

An RFC 3464 delivery-status notification follows the same private raw-receipt
path, but it is not a requester reply. Django recognizes only a top-level
`multipart/report; report-type=delivery-status`, extracts one embedded
application Message-ID, and matches only that Message-ID to the stable
outbound delivery. It never falls back to reply token, thread, references, or
subject matching. The receipt retains the strict reported Message-ID and, only
for an exact match, the opaque matched-delivery FK. Recipient matching compares
an ephemeral domain-separated fingerprint of each normalized RFC822
`Final-Recipient`
against the frozen recipient snapshot; it persists only an exact recipient FK
or unmatched/ambiguous state. The normalized rows retain only recipient
position, action, enhanced status, and match state—never the reported recipient
address, its fingerprint, or raw diagnostic prose.

## Enforced invariants

The schema migrations enforce the invariants that are practical at the
database layer:

- outbound and inbound direction/status combinations cannot mix;
- an outbound message always belongs to a request, while only unmatched or
  quarantined inbound evidence may temporarily lack one;
- approved-or-later outbound content has a complete approved snapshot;
- only the safety-net acknowledgment and non-statutory submission receipt may
  be marked automated;
- queued, sent, failed, and cancelled states carry their required timestamps;
- content and recipient snapshots cannot be rewritten after approval, including
  through normal queryset bulk operations;
- one delivery job exists per correspondence and sent jobs carry exactly one
  successful attempt number, completion time, and provider message ID;
- provider message IDs are unique within the configured provider/account scope;
- attempt numbers are positive and unique per delivery; completed attempts and
  attempt deletion are rejected;
- delivery-status notification rows are append-only, unique by receipt and
  recipient position, protected from conflict upserts, and constrain enhanced
  status classes to the reported action;
- inbound provider receipts are unique within provider scope and a completed
  match identifies its request, immutable content snapshot, method, and time;
- receipt parsing/matching combinations are exact: pending and failed evidence
  remains quarantined, parsed evidence has a content snapshot, and duplicate
  receipts retain only the earlier receipt link;
- an attachment cannot leave quarantine until its scan state is clean;
- only one unresolved clarification cycle exists per request; a resolution
  requires a received response, human resolver, substantive notes, and
  chronologically valid opened/responded/resolved timestamps. A withdrawn or
  abandoned terminal closure instead requires a substantive reason and records
  the cycle cancellation at the same instant as the canonical status event.

Cross-row and role-aware rules that cannot be expressed portably as database
checks are enforced by domain services and tested at their public entry points.
Only one unresolved requester-lifecycle delivery (acknowledgment,
clarification request, estimate revision, no-records closure, or denial) may
exist per request.
While it is pending, claimed, awaiting reconciliation, retryable, or failed,
later lifecycle queueing and request-state changes fail closed until an
officer resolves or cancels it.
The non-statutory submission receipt is deliberately outside that lifecycle
set, so it does not participate in the one-outstanding requester-lifecycle
constraint. Denial transport remains serialized against every other unresolved
delivery, including a submission receipt.
No serializer or view may implement correspondence business rules directly.

## Rendering and domain services

The template registry in `apps/correspondence/rendering.py` is an allowlist of
identifier/version pairs. Templates live below
`templates/correspondence/<identifier>/v<version>.txt`; changing legal language
requires adding a new version rather than rewriting the text used by an
existing approved snapshot. The current registry provides:

| Identifier | Version | Structured input |
|---|---:|---|
| `acknowledgment` | 2 | estimated completion date |
| `clarification_request` | 1 | substantive questions and response date |
| `estimate_revision` | 2 | previous/new dates and substantive reason |
| `installment_notice` | 3 | released package identity, scoped application download, expiry, item count, exemption/final flags |
| `submission_receipt` | 1 | request number, submitted description, explicit non-statutory disclaimer, officer contact |
| `no_records_closure` | 1 | determination, completion time, detailed search record, adequacy reason, retention reference |

Acknowledgment and estimate-revision version 2 are the current
requester-facing templates. They do not advertise the staff-only
`/requests/<number>` route because the application does not provide a
requester portal. Their immutable version 1 templates remain allowlisted so
historical content can be reproduced explicitly.

The renderer canonicalizes newlines, requires a non-empty body, rejects empty,
overlong, or newline-bearing subjects, and returns one plain-text
`RenderedMessage`. Generic authored drafts cannot impersonate the structured
legal-template kinds. Closure, denial, responsive-records, and general drafts
may retain officer-authored language without inventing an automatic legal
policy; approval still requires the Records Officer.

Installment template version 3 is requester-ready only after Django verifies a
released, unexpired package, its SHA-256/manifest evidence, any required
exemption log, fee-payment state, and the exact scoped application download
URL. Approval, queue, retry, and transport claim revalidate that snapshot.
Only a Records Officer may create or edit it.

## District-editable message templates

Every requester-facing outbound kind has an editable template, governed by
`apps/correspondence/automatic_templates.py` and administered from
`/configuration/message-templates` (Records Officer only). Versions are
immutable once activated, so any snapshot can be reproduced from the exact row
that produced it. Two families behave differently on purpose.

**Structured kinds** (`MANAGED_TEMPLATE_KINDS`: acknowledgment, submission
receipt, clarification request, estimate revision, installment notice,
no-records closure) render the requester's message from the template plus
validated structured inputs. The source-controlled built-in version stays the
fallback; once a version is activated, new drafts of that kind render from it
and carry `template_version = "managed:<uuid>"`. Because the safe renderer is
token-only (no `{% %}` logic), the structural parts of the built-in Django
templates are supplied as pre-rendered tokens instead:

| Token | Replaces |
|---|---|
| `previous_estimate_line` | the conditional previous-estimate line |
| `item_count_phrase` | the pluralized record count |
| `exemption_log_paragraph` | the RCW 42.56.210(3) exemption-log paragraph |
| `final_installment_paragraph` | the final-vs-more-installments paragraph |
| `search_steps` | the adequate-search step list |
| `retention_paragraph` | the out-of-retention paragraph |

**Free-form kinds** (`FREE_FORM_TEMPLATE_KINDS`: general,
responsive-records notice, closure, denial) stay human-authored. Their
template is a drafting starting point served by
`GET /api/staff/correspondence/template-prefill/` and offered in Compose as
"Start from district template". The officer edits it and the snapshot is built
from what the officer submits, so no authored kind acquires a machine-authored
legal record.

Editability does not relax a legal guarantee:

- `required_tokens` keeps mandatory content in the template source. An
  estimate revision cannot lose its revised date, an installment notice cannot
  lose its download link or expiry, and a no-records closure cannot lose its
  search evidence or its conditional legal paragraphs.
- `required_values` additionally rejects a *render* whose mandatory content
  resolves empty, while leaving legitimately-conditional paragraphs free to
  render blank.
- `required_phrases` keeps mandatory statutory sentences: the submission
  receipt must still distinguish itself from the five-business-day
  RCW 42.56.520 response, and the no-records closure must still state that it
  is not a determination that responsive records are exempt.
- Every subject must contain `{{ request_number }}`, unknown tokens are
  rejected per kind, and template syntax other than the allowlisted tokens is
  refused outright.
- Editing wording never widens automation. `AUTOMATED_CORRESPONDENCE_KINDS`
  still governs which kinds may be system-authored, auto-approved, and
  auto-queued, and it remains the acknowledgment and the submission receipt.

## Submission receipt: two paths, one guarantee

The submission receipt is explicitly non-statutory. It cannot set
`initial_response_delivered`, cannot transition the request, and cannot
satisfy or defer the day-5 response; it is absent from
`REQUEST_LIFECYCLE_EFFECT_KINDS`, and
`test_compliance.test_no_automated_path_exists` AST-guards both entry points
against acquiring a statutory effect.

`queue_submission_receipt()` is the automated path used at portal and email
intake. It requires `PRR_CORRESPONDENCE_AUTOMATED_OUTBOUND_ENABLED`, which is
off by default, so in the current deployment it does not reach requesters.
`create_officer_submission_receipt_draft()` is the human path behind
`POST /api/staff/correspondence/drafts/submission-receipt/`: it is attributed
to the officer, is `automated=False`, and follows the normal
approve/queue/deliver route. Only one receipt may exist per request; a
cancelled one may be replaced.

`apps/correspondence/services.py` is the only supported mutation boundary. It
provides draft creation/editing, exact preview, approval, queueing,
cancellation, retry, the safety-net acknowledgment path, delivery-success
effects, and human clarification resolution. The inbound service separately
owns explicit clarification-response association. Mutations lock the current
row and compare the caller's optimistic version. Draft audit entries retain
content hashes rather than copying requester-visible bodies into the broad
operational audit log.

Requester-facing acknowledgment and estimate-revision messages have no
synchronous Django-email fallback. `apps.records.letters.revise_estimate()`
retains the human-identity and substantive-reason guard, but now returns a
durable estimate-revision draft without changing the request, recording a
communicated revision, or sending anything. Staff and attributed staff agents
use `POST /api/staff/correspondence/drafts/estimate-revision/` for the same
draft-only outcome. Approval and queueing remain separate interactive Records
Officer actions, and only confirmed delivery applies the estimate.

## Staff and agent REST contract

`apps/api/resources/correspondence.py` exposes the application workflow without
duplicating domain rules in serializers:

- `GET /api/staff/correspondence/` lists PII-minimal timeline/operational
  metadata and accepts `request`, `direction`, `kind`, and `status` filters;
- `GET /api/staff/correspondence/<id>/` returns the authorized full record,
  exact content snapshots, recipients, attachments, and delivery state;
- `POST /api/staff/correspondence/drafts/<kind>/` creates one of the supported
  general, acknowledgment, clarification, estimate-revision, installment,
  responsive-records, closure, adequate-search no-records closure, or
  full-exemption denial drafts;
- `PATCH /api/staff/correspondence/<id>/` edits only a draft and requires its
  optimistic `expected_version`. General, responsive-records, closure, and
  denial drafts accept `subject`, `body`, and optional recipients; denial also
  requires a non-empty `exemption_citation_ids` list of active
  `ExemptionCitation` primary keys.
  Acknowledgment, clarification, estimate-revision, and installment
  drafts instead accept only their documented structured fields and
  optional recipients; Django re-renders the versioned template. Unknown or
  kind-inappropriate fields are rejected rather than ignored;
- `GET .../<id>/preview/` uses the same canonical rendering path as approval;
- `POST .../<id>/approve/`, `queue/`, `cancel/`, and `retry/` delegate to the
  locking domain services;
- `GET .../<id>/attempts/` returns sanitized attempt history and omits raw
  provider metadata;
- `POST /api/staff/correspondence-attachments/<id>/download/` issues a
  five-minute, user-bound URL only for a clean, released attachment; and
- `GET /api/staff/inbound-correspondence-receipts/?queue=unmatched` and
  `?queue=quarantined` expose officer-only, paginated review queues;
- `GET /api/staff/inbound-correspondence-receipts/<id>/` returns the retained
  safe matching evidence, parsed content, and any normalized delivery-status
  outcomes to an authorized officer;
- `POST .../<id>/match/` and `POST .../<id>/rematch/` require an interactive
  Records Officer, optimistic version, destination request number, substantive
  reason, and create attributed audit evidence;
- `POST .../<id>/redirect/` is the same correction for the commonest case: a
  requester followed up from a fresh thread, intake opened a new case for it,
  and the message actually belongs to a case that already exists. It takes the
  same interactive Records Officer, optimistic version, destination request
  number and substantive reason, applies only to an email-intake match, and in
  one transaction closes the automatically opened source case as not a records
  request—naming the destination in the closure reason—and moves the retained
  message and attachments to that destination. Either both happen or neither
  does: leaving the district with two open cases for one request would leave
  two five-day clocks running. Nothing is deleted and no requester message is
  sent;
- `POST .../<id>/associate-clarification/` requires an interactive Records
  Officer, optimistic version, an eligible open clarification-cycle ID, and a
  substantive reason. It reclassifies an already-matched general inbound
  message as that cycle's response but does not resolve the cycle or change
  request status;
- `POST /api/staff/requests/<number>/close-non-request/` lets a Records Officer
  administratively close only an auto-created email intake with a substantive
  reason. It preserves the request, raw receipt, correspondence, timeline, and
  audit evidence and cannot be reached through the generic status transition;
- `GET /api/staff/clarification-cycles/`, `GET .../<id>/`, and
  `POST .../<id>/resolve/` expose review and deliberate human resolution;
- `GET /api/staff/correspondence-operations/` returns PII-free delivery,
  inbound, quarantine, age, stuck-work, sanitized failure-category aggregates,
  and a cumulative count of unverified/advisory failed or delayed status-report
  rows; and
- `GET /api/staff/correspondence-operations/readiness/` returns only fixed
  readiness codes for the outbound switch, object storage, ClamAV, Redis task
  broker, and the enabled Gmail transport with its exact system principal.

A Liaison sees and drafts only for requests assigned through a collection task.
A Records Officer owns approval, queueing, closure/denial/installment drafts,
cancellation, retry, and clarification resolution. A version 3 installment
notice is approvable and deliverable only while its released package, scoped
download, fee state, integrity evidence, and exemption-log requirements remain
valid. Application Admin alone can inspect authorized operational state but
cannot perform those legal actions. Reviewer access is read-only.
Correspondence PII is not available to the nonstaff read-only MCP identity.

The two operations routes are read-only and restricted to Records Officers and
Application Admins. Liaison, Reviewer, anonymous, and nonstaff read-only-agent
requests are rejected. Their responses contain counts, ages, and fixed or
allowlisted categories only—never requester identities, message content,
filenames, storage configuration, endpoint names, or raw exceptions. The
**Configuration → Correspondence operations** page at
`/configuration/correspondence` shows the operational summary and readiness
checks to both roles. Records Officers also retain the PII-minimal outbound
transport queue there; Application Admins never load correspondence rows or
requester case data.

Deployment and incident automation can run
`python manage.py check_correspondence_readiness` for fixed-code text or add
`--json` for machine-readable output. The command probes the same dependencies
as the readiness route and exits nonzero unless every check is ready. The HTTP
route remains read-only and returns `200` with `ready: false` so authorized
staff can inspect which fixed check failed.

The staff application exposes daily correspondence work in two linked views:

- the case **Messages** tab contains a chronological, request-authorized
  conversation showing exact content, recipient summaries, delivery and
  matching state, safe attachments, sanitized attempts, clarification state,
  and any resulting request status event;
- **Inbox** is the cross-case queue for requester-message work, actionable
  unmatched/quarantined inbound receipts, and sanitized delivery exceptions.

The former `/correspondence` URL is compatibility-only. Request-scoped links
replace into case **Messages**, inbound receipt links replace into **Inbox**,
and unscoped Application Admin links replace into **Configuration →
Correspondence operations**. Failed, queued, draft, and delivery-status-report
transport bookmarks replace into the corresponding focused transport queue;
received-message bookmarks replace into the Inbox **Received** view. Transport
failures are never mislabeled as Inbox delivery-exception work.

Liaisons may prepare eligible drafts for assigned requests in **Messages**.
Records Officers
preview, approve, queue, cancel, retry, associate clarification responses, and
resolve in their authenticated session. Reviewers and Application Admins
receive only their authorized read-only operational view. Every button calls a
registered REST primitive; the exact frontend-operation set and capability
registry must remain equal.

The generic request-status control intentionally omits acknowledged, awaiting
clarification, denied, and closed-not-a-records-request. The domain rejects a
direct administrative attempt for the three communication-driven states with
`correspondence_delivery_required` and rejects the administrative non-request
status without canonical email-intake evidence; an attributed token
attempting the legacy denied transition receives the stricter `403
human_approval_required` handoff. A different client therefore cannot bypass
confirmed delivery. Denial is not an administrative status transition: an
interactive Records Officer must approve and queue the denial correspondence,
and only its first confirmed successful provider result moves the request to
denied. Each denial has persisted citation join rows with protected,
non-nullable `ExemptionCitation` foreign keys and human selection attribution.
Approval freezes a digest of the exact through-row identity, selector,
timestamp, and exemption taxonomy fields. Approval, initial queue, retry queue,
and the send claim require the citations to remain active and unchanged,
enforce the current second-review rule, and verify the frozen through rows
against that approval digest. Approval also requires every selected citation
to appear as a complete string in the requester-visible body. Matching
normalizes case and Unicode whitespace but rejects compatibility lookalikes and
partial matches inside a longer citation. The approval audit binds that basis
to the exact approved-body hash, which queue, claim, and result processing
revalidate. Once Django has issued the send claim, a provider
callback, any reconciliation claim, and the canonical denied transition verify
only the frozen recipient/basis rows and approval evidence. A later taxonomy or
requester-contact edit cannot roll back proof of a message Gmail may already
have accepted, but corruption of the frozen rows or approval audit still fails
closed.
The exact current requester must be a `To` recipient at approval, queue/retry,
and send claim. A counsel-only `To`, requester only in `Cc`, or a stale
requester identity/address is rejected. A contact change before claim requires
a replacement; one after a send claim cannot block reconciliation or erase
genuine transport evidence.
A citation marked `requires_second_review` cannot be approved until the product
has separate persisted second-review evidence; one officer's approval is not
treated as that evidence. A queued, failed, unknown, or cancelled denial has no
request-status effect.

`denied` means fully exempt in the request state machine. A no-records or
out-of-retention determination uses the separate append-only
`AdequateSearchAttestation` and versioned `no_records_closure` route, never an
exemption citation. Creation requires an interactive Records Officer, complete
collection tasks, detailed search steps, a substantive adequacy reason, and a
district-counsel approval reference. Outside-retention findings add an expired
preservation review, verified retention reference, and four obvious-lead
checks. Approval revalidates the task snapshot; only confirmed delivery
applies `closed_no_records`. See `docs/no-records-closure.md`.
While a request is in clarification, the generic status control disappears
entirely: an open clarification cannot be moved between working states at all.
Returning the request to active work requires the dedicated cycle-resolution
service, a received response, and substantive notes. Any other transition
returns `409 clarification_resolution_required`. The way out for a requester
who withdrew, or a clarification period that expired, is the Close case
control, which offers only withdrawn and abandoned. That closure locks and
cancels the open cycle atomically with the canonical status transition and
records the staff actor and substantive reason; it does not fabricate a
clarification response.

Withdrawal and abandonment are open to every workflow staff role—Records
Officer, Department Liaison, Reviewer, Application Admin—through
`POST /api/staff/requests/<number>/close/`. They record what the requester
did rather than a legal determination about the records, and the substantive
written reason plus the append-only audit entry naming the actor are what make
them accountable. Fulfilment still requires a current Records Officer and a
substantive case-specific reason, as do the no-responsive-records and
not-a-records-request closures and every reopen; Application Admin authority
alone is insufficient for those. Denied is excluded because it is delivery-driven as
described above.

Every operation intended for an agent or the staff GUI has a stable row in
`apps/api/capabilities.py`. Attributed staff tokens may assist with authorized
drafting and preview, including preparation of a reasoned estimate-revision
draft. Approval, queueing, clarification-response association, clarification
resolution, and camera exclusions require an interactive staff session: token
calls receive `403 human_approval_required` plus the capability id, action, and
required role. A token cannot replace delivery evidence with a direct denied
transition. This is a handoff contract, not an alternate approval mechanism.

## Immutable content and corrections

Preview and delivery use the same canonical `RenderedMessage`. Approval copies
the exact rendered subject/body and structured metadata into the approved
snapshot and freezes content, template identity, request association,
Message-ID, reply token, and recipients. Queueing revalidates every recipient
and requires every attachment to be clean and released from quarantine. A
correction is a new correspondence linked and audited as a replacement; it is
never an edit to a sent or approved record.
Approval also records a SHA-256 digest and count over the exact recipient rows.
The transport claim recomputes and compares that evidence, so a forged or
legacy approval record cannot authorize a send.

Inbound subject/body are evidence and freeze immediately. Raw message bytes
remain private object-store evidence and are never served directly.

## Delivery, idempotency, and reconciliation

Django assigns one RFC Message-ID before a message is approved. Its form is
deterministic from the correspondence UUID and the configured
`PRR_CORRESPONDENCE_MESSAGE_ID_DOMAIN` (default `prr.psd401.net`). The opaque
reply token is independently random and frozen with the message. Django
constructs the stable Reply-To address as
`<PRR_CORRESPONDENCE_REPLY_LOCAL_PART>+<reply_token>@<PRR_CORRESPONDENCE_REPLY_DOMAIN>`.
Retries never change either header.

A queued delivery has one application idempotency key. Claim uses row locking
and a bounded lease. The result service fingerprints normalized durable
evidence: timestamps are compared as UTC instants, `sent` and `reconciled` are
the same success evidence on a reconciliation claim, allowlisted provider
metadata is canonicalized, and raw `provider_error` is discarded. Replaying
equivalent evidence is idempotent; changing durable provider identifiers,
failure category, timestamp instant, or safe metadata conflicts. Legal effects
apply only on the first valid success. If Gmail may have sent but worker result
recording was lost, lease recovery moves the job to
`awaiting_reconciliation`; the next worker searches Gmail by the existing
Message-ID and reports the reconciled result without sending again. It never
creates a replacement delivery or a new Message-ID.

Successful evidence must carry the original aware provider timestamp. For a
send claim it may be at most five minutes before the claim; for reconciliation
it may be at most five minutes before the delivery was queued. It may never be
later than the result callback. For acknowledgment, clarification,
estimate-revision, or denial correspondence, it also cannot predate request
receipt or the request's latest recorded lifecycle communication. These bounds
prevent backdating and future-dating legal effects while allowing bounded
provider clock skew. An identical result already committed to the attempt
remains idempotent even if later request activity has advanced that lifecycle
floor.

Every claim/result attempt records sanitized metadata only. Message bodies,
requester addresses, tokens, storage keys, and raw provider errors do not
belong in logs or operational task metadata.

Queueing registers an in-process Celery enqueue with
`transaction.on_commit()`. A rolled-back queue therefore creates neither a
delivery nor a task. Enqueue suppression uses only the opaque delivery UUID and
current `attempt_count`; this prevents overlapping watchdog ticks from piling
up duplicate work while allowing a later reconciliation generation to run.
If Redis or the broker is unavailable after commit, the durable pending
delivery remains authoritative and the minute watchdog retries it after the
configured recovery interval. No requester, recipient, subject, body,
attachment, reply token, or request description enters the enqueue key or task
arguments.

### Drain switch and stuck-delivery watchdog

`PRR_CORRESPONDENCE_OUTBOUND_ENABLED` defaults to `false` and is a strict
boolean deployment drain switch. When false, Django rejects every new queue,
staff retry, and worker claim before mutating delivery state. Staff queue/retry
returns `503 outbound_transport_disabled`; the integration claim contract
returns the same fixed code with `Retry-After: 60`. Drafting, preview, and
approval may continue because none claims that transport occurred. Public and
email intake also continue accepting legal requests; their non-statutory
submission receipt is skipped without leaving draft or delivery rows.

Turning the switch off does not abandon work that may already have reached
Gmail. A result for an existing active lease remains accepted and idempotent,
and the owning system principal may continue reading approved attachments
during that lease. Staff may cancel an eligible pending,
retryable, or failed unsent delivery; active claims cannot be cancelled.
The watchdog still finalizes an expired claim as append-only `lease_expired`
evidence and moves the same delivery to `awaiting_reconciliation`, but it
suppresses the follow-up task while outbound transport is disabled. These
exceptions let operators drain safely without losing provider evidence or
creating contradictory legal state.

The minute beat task
`apps.correspondence.tasks.watch_stuck_correspondence_deliveries` performs
bounded recovery. When transport is enabled, it finds an unclaimed `pending`
or `awaiting_reconciliation` delivery after
`PRR_CORRESPONDENCE_STUCK_SECONDS`, and it always finds expired send or
reconciliation leases. Expiry finalizes only the existing attempt; recovery
itself never sends mail, creates an attempt, creates a replacement delivery,
changes the Message-ID, or applies a request lifecycle effect. It enqueues the
opaque delivery UUID and current attempt generation so the worker must claim
it; an expired or unknown prior attempt can only proceed
through Message-ID reconciliation, not an automatic resend.

Each queue, retry, unknown result, suppression, or nudge advances the
delivery's durable `recovery_not_before` clock. This rate-limits recurring
nudges to at most one per configured stuck interval. A shared Redis marker
keyed by delivery UUID and `attempt_count` suppresses a duplicate task while
still allowing a later reconciliation generation. If Redis or the task broker
is unavailable, expired lease evidence still commits; the watchdog records a
bounded notification failure and tries no sooner than the next interval.
Terminal, failed, and
human-retryable deliveries are not auto-retried. The task returns aggregate
counts only: expired claims, nudged deliveries, suppressed nudges, and
notification failures.

If an expired delivery does not match its claimed open attempt, the watchdog
does not repair, finalize, or replace that evidence. It logs a generic
inconsistency, advances only that delivery's recovery clock by one interval,
and lets later batch candidates proceed. An operator must investigate the
database and retained provider evidence; never synthesize an attempt or
callback to clear the warning.

### In-process outbound transport boundary

The Gmail sender calls the claim, attachment, and result services directly under
the migration-provisioned `prr-gmail-outbound-transport` principal. That
principal is non-login, has no token, and holds exactly
`correspondence.deliver_outbound_correspondence`. Claim payloads contain frozen
attachment metadata and internal IDs; the worker reads each object through the
claim-bound service and verifies its size and SHA-256 before composing MIME. No
claim, result, or attachment transport route is exposed over HTTP.

Migration `records.0016_retire_legacy_integration` revokes exact-scope legacy
transport tokens and removes their provisioning commands. The checked-in legacy
contract artifacts are historical only and must not be activated.

## Request lifecycle effects

Queueing never proves communication. Only the first successful result callback
may apply a communication-dependent effect:

- acknowledgment: call `record_acknowledgment()` and transition from received
  only after Gmail success;
- clarification request: open the cycle and transition through
  `services.transition()` only after Gmail success;
- estimate revision: draft preparation requires a human-attributed staff
  identity and substantive reason; approval and queueing require an interactive
  Records Officer, and only success records the communicated revision;
- full-exemption denial: an interactive Records Officer selects at least one
  active exemption citation, approves and queues the frozen denial, and only
  its first confirmed successful result transitions the request to denied
  through the canonical lifecycle service;
- no-records/out-of-retention closure: an interactive Records Officer records
  immutable adequate-search evidence and counsel approval, approves and queues
  the versioned message, and only its first confirmed successful result
  transitions the request to `closed_no_records`;
- administrative terminal closure: fulfilled, withdrawn, and abandoned
  require a current Records Officer plus a substantive case-specific reason;
  they are not delivery-success effects; and
- inbound clarification response: deterministic evidence may associate a
  response automatically, or a Records Officer may explicitly associate an
  already-matched general message with one eligible open cycle. Neither path
  resolves the cycle or changes request status.

The provider's confirmed send instant, not callback or reconciliation time,
timestamps the acknowledgment and transition `StatusEvent`s, clarification
cycle, estimate revision, denial transition, and communicated correspondence.
Clarification tolling therefore starts on the Pacific calendar date when the
requester was actually sent the question even if the callback is recovered
days later.
When an acknowledgment communicates an estimate already present on the
request, Django links and timestamps the matching uncommunicated
`EstimateRevision`. If no matching evidence row exists, it creates a
conservative initial evidence row; it does not duplicate estimate evidence
that was already communicated.

The day-five safety net remains the only automated statutory response. It may
create, approve, and queue an acknowledgment, but it still cannot claim that
the letter was sent or update the request until delivery succeeds. The only
other automated requester-facing message is the submission receipt queued for
portal and email intake. Its rendered body expressly disclaims statutory
effect, it never sets `initial_response_delivered` or transitions request
status, and it does not satisfy or defer the safety net.
It considers either a delivered acknowledgment or a delivered clarification
request a valid initial statutory response. That fact is derived from the
append-only status-event history, so resolving a clarification later does not
make the request eligible for a redundant safety-net acknowledgment or overdue
alert. The queue service repeats the same check under the locked request row to
close the race between the hourly selection and a concurrent delivery result.
Repeated safety-net runs reuse the existing delivery rather than create a new
Message-ID. An initial default estimate is recorded as communicated only when
that acknowledgment actually succeeds. A newly queued safety-net delivery
emits the queue-time-only `AUTO_ACK_QUEUED` operational notice. If transport is
disabled or existing acknowledgment evidence requires human review, the task
rolls back the attempted queue, emits `AUTO_ACK_BLOCKED`, continues checking
other at-risk requests, and waits for an officer to restore transport or
resolve the evidence.

`EstimateRevision.correspondence` links a communicated revision to its immutable
message, and `communicated_at` is the successful send time. Rows predating the
correspondence cutover retain null links or timestamps when no trustworthy
delivery evidence can be reconstructed. A human-attributed draft requires a
substantive reason; an interactive Records Officer freezes and queues the
immutable snapshot. Its previous date must still match the locked request at
approval, queue, and retry. A revision cannot overtake an unresolved lifecycle
delivery; after any intervening revision the stale message must be recreated
from the current estimate.
Delivery success still applies that already-approved effect if the approving
officer is deactivated while a retry or reconciliation is pending; otherwise
the internal deadline would diverge from the estimate already communicated.

Clarification success creates exactly one open `ClarificationCycle` and reaches
the clarification request status only through `apps.records.services.transition`.
An inbound reply may later populate `responded_at`. When strong automatic
evidence matched only the request and left the message classified as general,
an interactive Records Officer may select the open cycle and record a
substantive reason through the explicit association action. The message must
already be matched to the same request and its provider timestamp must fall
within the cycle's eligible response window. Association is evidentiary only:
it does not resolve the cycle or transition the request.
`resolve_clarification()` separately requires a current Records Officer, the
linked inbound response, and substantive notes before transitioning the
request back to gathering.

A request cannot close while any delivery is pending, claimed, awaiting
reconciliation, retryable, or failed; an officer must first resolve or cancel
the unsent correspondence. Closed requests cannot be reopened by the lifecycle
service, cannot queue/retry/claim a new send, and a stale successful
clarification/acknowledgment/estimate/denial callback rolls back rather than
leaving a closed timestamp beside a contradictory communication state.

## Correspondence configuration

Every value in this section is a **district setting**, changed at
**Configuration > District settings** by an Application Admin with a written
reason and a permanent history, and taking effect across web, workers, and
beat within seconds. The bounds quoted below are enforced when the change is
saved, with the limit in the refusal; none of them is an environment variable
any more, and setting one in `.env.app` does nothing. The two exceptions are
`PRR_ENVIRONMENT` and the ClamAV address, which are environment, not district
policy.

- `PRR_CORRESPONDENCE_MESSAGE_ID_DOMAIN` is a validated DNS name used only for
  deterministic application-generated Message-IDs.
- `PRR_CORRESPONDENCE_REPLY_LOCAL_PART` is the safe base local part for reply
  routing (default `publicrecords`).
- `PRR_CORRESPONDENCE_REPLY_DOMAIN` is the domain that receives tagged replies;
  it defaults to the Message-ID domain.
- `PRR_ENVIRONMENT` is a non-secret 1-64 character deployment label included in
  opaque queue events.
- `PRR_CORRESPONDENCE_OUTBOUND_ENABLED` is a strict boolean that defaults to
  `false`. It blocks new queue, retry, and claim work while preserving result
  callbacks, eligible cancellation, expired-lease finalization, and
  active-lease attachment reads needed to drain safely.
- `PRR_CORRESPONDENCE_STUCK_SECONDS` is the 300-86400 second age and recurring
  nudge interval for stuck delivery recovery (default 3600). It also initializes
  or advances each delivery's durable `recovery_not_before` time.
- `PRR_GMAIL_INBOUND_POLL_ENABLED` is a strict boolean that defaults to
  `false`. The minute poll task returns before principal or Gmail lookup when
  it is false. Only production normally enables it.
- `PRR_GMAIL_INBOUND_PROCESSED_LABEL` is the safe internal label applied after
  durable receipt (default `PRR/Processed`).
- `PRR_GMAIL_INBOUND_ARCHIVE_PROCESSED` is a strict boolean that defaults to
  `false`. When true, the same `messages.modify` call that applies the
  processed label also removes `INBOX`, so a handled message leaves the
  mailbox inbox. It runs only after durable receipt, changes no application
  state, and the poll query already excludes labelled messages, so enabling or
  disabling it never changes which messages are processed.
- `PRR_GMAIL_INBOUND_LOOKBACK_DAYS` bounds missing/expired-history resyncs to
  1-30 days (default 7). Non-production resyncs additionally require the
  internal `PRR/<environment>` Gmail label.
- `PRR_GMAIL_INBOUND_STALE_SECONDS` bounds checkpoint freshness for the
  requester-data-free operational status command to 120-3600 seconds (default
  300).
- `PRR_CLOUDWATCH_METRICS_ENABLED` is a strict boolean that defaults to
  `false`; the AWS runtime overlay enables it. Each poll emits health, enabled
  state, duration, bounded outcome counts, and a fixed failure category to the
  `PSD401/PRR` namespace without mailbox or requester identifiers.
- `PRR_CLOUDWATCH_REGION` is the validated AWS region used only when that
  telemetry is enabled.
- `PRR_CORRESPONDENCE_LEASE_SECONDS` bounds a claim to 30-3600 seconds
  (default 300).
- `PRR_CORRESPONDENCE_ATTACHMENT_MAX_COUNT`,
  `PRR_CORRESPONDENCE_ATTACHMENT_MAX_BYTES`, and
  `PRR_CORRESPONDENCE_ATTACHMENT_TOTAL_MAX_BYTES` bound a frozen outbound
  message to at most 10 files, 25 MiB per file, and 50 MiB combined. Deployment
  overrides may only tighten those version 1 limits.
- `PRR_OBJECT_STORE_CONNECT_TIMEOUT_SECONDS` (default 5, allowed 1-30),
  `PRR_OBJECT_STORE_READ_TIMEOUT_SECONDS` (default 30, allowed 1-120), and
  `PRR_OBJECT_STORE_MAX_ATTEMPTS` (default 3, allowed 1-5) bound every
  application S3/MinIO data-plane call. Retries use the SDK's standard mode
  with the configured total-attempt cap.
- The Settings page's malware scan timeout bounds each private scanner
  connection/read (default 30, allowed 1-120). Invalid or out-of-range
  storage and scanner values are refused when saved.
- `PRR_EVENT_OUTBOX_STALE_SECONDS` is the 30-3600 second lease before a
  committed event whose dispatched task disappeared is re-enqueued; failed
  HTTP attempts also use persisted exponential `next_attempt_at` backoff
  (default 300).
- `PRR_CORRESPONDENCE_INBOUND_MESSAGE_MAX_BYTES` and
  `PRR_CORRESPONDENCE_INBOUND_METADATA_MAX_BYTES` bound the streamed RFC822
  part and its strict JSON envelope (defaults 75 MiB and 16 KiB).
  The shipped Gunicorn worker timeout is 300 seconds. The trusted reverse proxy
  must allow at least the configured message limit plus multipart overhead
  (80 MiB for the defaults) and use a slightly longer bounded upstream
  timeout. Lower the application limit when a platform cannot support those
  bounds; do not make proxy limits unlimited.
- `PRR_CORRESPONDENCE_INBOUND_BODY_MAX_BYTES`,
  `PRR_CORRESPONDENCE_INBOUND_MAX_HEADERS`,
  `PRR_CORRESPONDENCE_INBOUND_MAX_HEADER_LINE_BYTES`,
  `PRR_CORRESPONDENCE_INBOUND_MAX_MIME_PARTS`, and
  `PRR_CORRESPONDENCE_INBOUND_MAX_MIME_DEPTH` bound parsing independently of
  the transport request limit.
- `PRR_CORRESPONDENCE_ATTACHMENT_SCAN_STALE_SECONDS` is the 30-3600 second
  recovery age for quarantined attachment scan work whose initial broker
  dispatch or retry disappeared (default 300). The minute beat task requeues a
  bounded batch; it never marks a file clean.
- `PRR_CORRESPONDENCE_INBOUND_RESERVATION_STALE_SECONDS` is the 300-86400
  second grace period before the minute recovery sweep may lease and delete a
  quarantine write that was never atomically adopted by a receipt or
  attachment (default 900). Recovery cross-checks both exact domain key
  references before deletion and records a PII-free audit event. A separate
  internal one-hour processing lease is committed before each storage I/O.
  Django reacquires and rechecks the writer lock before the PUT. It holds that
  lock through the PUT and marks the generation stored in the same
  transaction. The lease is refreshed after parsing, after each attachment
  stage, and immediately before adoption. Cleanup requires both the created-at
  grace period and that processing lease to have expired.
- The portal address, the records officer contact address, and the default
  response estimate (all Settings-page values) provide existing template
  context.

### Secure outbox cutover

This is a domain-invariant checklist for the future tested deployment
mechanism, not an approved standalone procedure. Recurring production changes
remain blocked by `docs/aws-deploy.md`; do not execute these steps manually.
The migration-free recurring image-replacement path cannot perform this
schema-bearing cutover. It remains blocked until a separately reviewed
migration-bearing mechanism has retained isolated restore evidence and an
explicit database rollback plan.
The mechanism must hold the global deployment lock, stage an exact merged SHA,
prove a fresh backup and retained restore evidence, and record common-image and
rollback provenance while it enforces this coordinated stop:

1. Before activating the exact staged release, retain and verify the
   digest-addressable old release for rollback. Put the application in
   maintenance mode. While the old release is still available, verify that
   there are no `CorrespondenceDeliveryAttempt` rows and no non-cancelled
   `CorrespondenceDelivery` rows. Resolve or cancel eligible unsent rows
   through a supported application path; preserve and escalate any sent or
   evidentiary row. Never delete rows, invent provider evidence, or use a raw
   database update. Migration 0003 aborts with up to ten offending IDs if this
   preflight is not empty. Then stop old web and beat producers and drain every
   active, reserved, scheduled, and broker-queued task through the old workers.
   Stop those workers only after every queue is empty. An already-running old
   task has the former terminal-state rules.
2. Take and verify a restorable database backup. Apply migrations, then start
   only web from the new release under maintenance mode with
   `PRR_CORRESPONDENCE_OUTBOUND_ENABLED=false`.
   The correspondence migration refuses to carry active or evidentiary
   pre-contract delivery state into the immutable v1 attempt contract. It also
   invalidates draft installment-template-v1 text, advances those rows to
   template version 2 with an inert review message, and increments their
   optimistic version. A Records Officer must edit such a draft through the
   structured installment action before further use. Frozen non-draft v1
   correspondence is preserved as evidence but cannot enter the v2 delivery
   path; create an audited replacement if one is still needed.
3. Configure the keyless Gmail identity with the global Gmail switch and both
   direction switches false. Keep `PRR_STAFF_NOTIFICATIONS_ENABLED=false` too.
   Run `python manage.py verify_gmail` and require the pinned mailbox, two exact
   scopes, and profile checks to pass without sending mail.
4. After a named operator approves that credential result, set only
   `PRR_GMAIL_ENABLED=true`; keep inbound, outbound, and staff notifications
   false. Start worker and beat from the same release and recreate web so all
   three receive the same settings. Run
   `python manage.py check_correspondence_readiness --json`. At
   this point a deliberate `outbound_transport: disabled` is expected; every
   other check must be ready. The command emits only fixed codes and exits
   nonzero whenever any check is not ready.
5. Run the complete local/CI transport contract suite with isolated provider
   doubles and test data. Require proof that the in-process task claims the
   delivery, preserves its RFC Message-ID, respects recipient restrictions,
   and reports its result through the existing service.
6. Enable only production outbound after that proof and named operator
   approval; keep inbound disabled until its separate acceptance. Restart web,
   worker, and beat together and require a ready command result. A production
   integration smoke test must use an explicitly
   district-controlled synthetic request and non-requester address; never swap
   the address on an existing case. Verify one queue/task/result cycle and the
   same delivery and Message-ID in the operations view, then carry the synthetic
   case through its supported human disposition. Preserve the resulting
   evidence; never delete or rewrite the immutable request/correspondence rows.

For a named operational incident drain, first record the running common image
and incident owner, set `PRR_CORRESPONDENCE_OUTBOUND_ENABLED=false`, and recreate
web, worker, and beat from that same image as one serialized emergency action;
do not build or change any other setting.
New queues, retries, and worker claims now fail closed, while an already leased
worker can read its approved attachments and submit its result. Let active
leases report or expire; the watchdog finalizes expired attempt evidence
without issuing a new nudge. Cancel only eligible unsent work through the staff
action—never an active claim—and use the PII-free operations endpoint until
claimed work is drained. Resuming is not an emergency-disable action: it must
wait for and run inside the tested, globally locked deployment mechanism in
`docs/aws-deploy.md`. That mechanism verifies Gmail, enables outbound,
recreates all three process classes together, requires readiness, and lets the
watchdog nudge the same pending/reconciliation delivery.

A code/schema rollback before production acceptance must additionally enter
maintenance, drain all new workers and the broker, stop the workers, and
restore the verified pre-cutover database backup before starting the retained
old release. New delivery tasks carry a dispatch token that the old worker
cannot accept. Once any production correspondence or other legal write has
been accepted on the new release, restoring that snapshot would discard legal
records; preserve the database and use a forward fix instead. Never run an old
dispatcher against new-release rows or rebuild a mutable branch as a substitute
for the retained artifact. The reverse migration also refuses to expose any
installment-template-v2 row to the old renderer.

Migration 0004 is also a fail-closed evidence boundary. Before applying it,
verify that each of these checks is empty:

- every legacy `InboundCorrespondenceReceipt`;
- every `Correspondence` with `direction="inbound"`;
- every `CorrespondenceAttachment` whose correspondence is inbound;
- attachment storage keys whose `Count("id")` is greater than one; and
- every attachment outside the exact scan evidence states: pending is
  quarantined with an empty reason and no timestamp; clean is released with an
  empty reason and a scan timestamp at or after creation; infected/error is
  quarantined with a nonempty reason and a scan timestamp at or after creation.

The migration refuses to invent idempotency, raw-storage,
submitting-identity, parsed-header, attachment-provenance, or scan-verdict
evidence and reports bounded offending IDs or duplicate keys. Reconcile the
rows and keys explicitly before cutover; never delete legal evidence, rewrite
attachment verdicts merely to force rollback, or let a migration silently
select an object. Start the new web/worker/beat release together before
enabling inbound polling. After any version 1 inbound receipt is accepted,
the reverse migration refuses to discard it; rollback uses the verified
pre-cutover backup or a forward fix, never row deletion.

Migration 0005 is a second fail-closed evidence boundary. Its reverse migration
refuses whenever any pending or completed cleanup ledger row exists, because
dropping such a row would discard durable quarantine cleanup work and attempt
evidence. Once cleanup work has been recorded, use a forward fix; do not delete
ledger rows to force a reverse migration.

Migration 0006 adds the pre-I/O inbound quarantine reservation and transport
alias ledgers. Apply it while inbound submission is disabled, then start web,
worker, and beat from the same release before enabling or re-enabling the
inbound poller. Its reverse migration refuses as soon as any reservation
generation or `InboundQuarantineTransportAlias` exists; alias-only evidence
also blocks reversal. Unstored, stored, adopted, pending-cleanup, completed,
and transport alias rows are all security and recovery evidence. Before the
first reservation or alias only, the coordinated deployment may roll back the
schema with the old services still stopped. Afterward, restore the verified
pre-cutover backup only if no production legal write would be lost; otherwise
preserve both ledgers and use a forward fix. Never delete reservations,
transport aliases, or object versions to force a reverse migration.

Migration 0007 adds the nullable, indexed `recovery_not_before` clock used to
rate-limit delivery watchdog nudges. It does not rewrite approved content,
attempt evidence, provider identifiers, or legal effects. Deploy web, worker,
and beat from the same release before enabling outbound.

Migration 0008 adds the append-only delivery-notification evidence table and
the DSN correspondence/match choices. Apply it before routing DSNs into the
inbound workflow. Its reverse migration refuses after any notification row,
any `delivery_status_notification` correspondence, or any receipt with
delivery-status matching fields exists. This includes an unmatched DSN with no
normalized notification rows. Use a forward fix or a verified pre-cutover
restore only when no accepted legal write would be lost. Never delete DSN
correspondence, receipt state, or notification rows to force rollback.

Migration 0009 adds `CorrespondenceDenialCitation`. Existing denial drafts
remain drafts and must be edited through the supported draft action to select
at least one active exemption before approval; no migration invents a legal
basis. Any unsent approved or claimable legacy denial must be cancelled under
the old release and replaced through the audited new workflow; never send it
merely to clear a migration gate, and never fabricate through rows or audit
detail. A legacy denial already sent remains historical evidence. The reverse
migration refuses after any denial-citation row exists, including draft
legal-basis evidence. Preserve those rows and use a forward fix; never delete a
basis to force reversal.

Migration 0011 is a forward deployment gate for recipient approval evidence.
Before applying it from a release that did not record
`recipient_snapshot_sha256`, drain eligible outbound correspondence in
`approved`, `queued`, or `failed` state to `sent`, cancel it through the
supported action, or cancel it and preserve a replacement draft for approval
after upgrade. The migration requires exactly one `correspondence.approved`
audit row. Its positive integer recipient count must equal the number of
recipient rows, and its SHA-256 digest must exactly equal the digest recomputed
from the canonical, ID-ordered recipient snapshot used by the runtime claim
gate. A merely well-formed but mismatched digest is rejected. The migration
reports bounded offending correspondence IDs and refuses to backfill legal
evidence. Its reverse is intentionally a no-op because it adds no schema and
erases no evidence. That does not make an old release safe after new work is
accepted: use a forward fix after cutover rather than restoring old code that
lacks runtime snapshot verification.

Records migration 0008 adds the typed `StatusEvent.correspondence_effect`
field and a database constraint tying each nonblank effect to its permitted
status-event shape. Correspondence migration 0012 then fails closed unless
every sent acknowledgment, clarification request, estimate revision, and
denial has one already-linked event and an exact, internally consistent
request, actor, timestamp, finalized-delivery, provider-result, and
kind-specific legal-evidence graph. It accepts the exact legacy
acknowledgment pair produced by the prior release, but no approximation.
Only after the whole preflight succeeds does it label those existing events
and make the result-event link one-to-one. It never creates an event, chooses
between candidates, or repairs/rebinds a link.

Do not delete, synthesize, or raw-edit legal evidence to force migration 0012.
Review a reported, bounded correspondence ID under the prior release and use a
supported forward correction, or restore the verified pre-cutover backup.
Reversing correspondence 0012 removes the one-to-one schema constraint but
intentionally does not erase the typed event labels; reversing records 0008
therefore refuses while any such label exists. An old release is not a safe
rollback after typed correspondence evidence has been accepted.

Requester-facing acknowledgment and estimate-revision delivery now use only
the durable correspondence queue. The old synchronous renderer, requester-mail
helpers, request-level estimate mutation action, and their letter templates
have been removed. Internal operational alerts use a separate mailbox-pinned
Gmail path with its own global/staff gates and do not represent requester
communication.

## Inbound Gmail transport, parsing, and matching

`apps.correspondence.tasks.poll_inbound_gmail` runs every minute. It exits with
zero Gmail calls while inbound polling is disabled. Otherwise it loads the
migration-provisioned `prr-gmail-inbound-transport` principal, which is
non-login, has no token, and holds exactly
`correspondence.submit_inbound_correspondence`.

`GmailSyncState` stores one Gmail `historyId` per configured mailbox and
`PRR_ENVIRONMENT`. Production incrementally requests only messages added to
Inbox. A missing or expired checkpoint first reads a history boundary, then
lists unprocessed Inbox messages inside the configured lookback window; that
ordering prevents a message arriving during resync from being skipped.
Non-production always uses the bounded query and requires its internal
`PRR/<environment>` label, so an accidentally enabled dev poller cannot consume
unlabeled production mail.

Each Gmail message is fetched once as original RFC822 bytes plus its provider
message ID, thread ID, history ID, and authoritative `internalDate`. The task
passes those bytes into `receive_inbound_message()` under the system principal.
Only bounded `Delivered-To`/`X-Original-To` routing headers are considered for
tokenized reply routing; MIME `To`/`Cc` remain untrusted content. The message is
labeled processed only after durable receipt. Provider/read/receiving failure
leaves the checkpoint unchanged; a label-only failure is logged after durable
receipt and does not turn a successful legal acceptance into a failure.
Provider-message uniqueness and payload digests make checkpoint loss,
overlapping ticks, and history resync safe replays rather than duplicate legal
records.

After deterministic matching, one narrow intake rule applies. A parsed,
released, non-DSN message whose sole routing recipient is the bare configured
mailbox becomes an email-channel request only when it has one valid sender, a
non-empty parsed body, no existing request match, no automated `Auto-Submitted`
value, no `Precedence: bulk|list|junk`, and no `List-Id`. Tokenized replies and
all rejected mail retain their normal matched or review-queue state. Eligible
mail is claimed atomically with `submit_intake()`: Gmail `internalDate` becomes
the received time, parsed sender identity is minimized into the requester row,
and the exact parsed text becomes the immutable description. The canonical
pipeline supplies deadline calculation, triage/routing, footage holds,
submission receipt, and audit. Receipt replay returns the existing request.

Each email attachment has one retained correspondence object and one malware
scan. Its linked `IntakeAttachment` representation points back to that source;
downloads consult the source verdict and storage key at access time so pending,
infected, error, or re-quarantined evidence fails closed without rescanning.

### In-process inbound receiving boundary

The Gmail poller calls `receive_inbound_message()` directly under the
migration-provisioned `prr-gmail-inbound-transport` principal. That principal
is non-login, has no token, and holds exactly
`correspondence.submit_inbound_correspondence`. Provider identity and immutable
RFC822 evidence still use the same reservation, quarantine, safe parsing, DSN,
and deterministic matching services described below; no inbound transport route
is exposed over HTTP.

## Attachment boundary

Correspondence attachments have application-generated object keys, bounded
frozen metadata, sanitized filenames, quarantine/scan state, and clean-only
download or delivery. Claim-time delivery takes a row-locked local snapshot
and verifies the stored object against its frozen byte count and SHA-256 before
exposing any bytes. Remote URLs are never fetched and filenames never become
object keys.

There is no caller-facing outbound-attachment create or upload endpoint. Only
an attachment created by a trusted application-owned ingest/scan path and
marked clean may enter a claim; test fixtures that create rows directly do not
define a production ingest contract.

Inbound MIME attachments are decoded under count/per-file/combined limits,
given sanitized display names, classified from their bytes rather than a
hostile MIME label, hashed, and stored as inert octet streams under generated
quarantine keys through the same committed-before-I/O reservation boundary.
Before Python constructs the MIME tree, the raw preflight counts RFC 3464
delivery-status field blocks, rejects unsupported `message/*` subtypes, and
walks any literal RFC822 tree visible behind a transfer-encoding label. This
keeps the configured aggregate part/header/depth limits authoritative even for
parser-specific pseudo-parts; ordinary and base64/quoted-printable
`message/rfc822` attachments remain supported.
A valid decoded attachment may contain zero bytes; its zero-byte reservation,
empty-content digest, single `PutObject`, and later scan still follow the same
fail-closed path. Raw RFC822 submissions remain non-empty. The private ClamAV
task streams and re-verifies exact size/digest. A clean verdict first copies the
object, then commits the database CAS, audit row, and durable post-verdict
quarantine-cleanup work atomically. Infected verdicts record the same cleanup
work with their audit evidence. Deletion runs only after commit.

Two distinct leased recovery sweeps protect this boundary. The reservation
sweep considers only unadopted generations whose created-at grace period and
processing lease have both expired, takes an expiring cleanup lease, and
cross-checks the exact key, size, and digest against receipt or attachment
domain evidence. Live processing follows the pre-I/O lease and the writer lock
held across the PUT and stored mark above. An exact retry that encounters a
cleanup-owned reservation gets retryable `submission_in_progress`; it cannot
race a delete.
An exact domain reference is healed by recording adoption in the same
transaction as its audit, never deleted; no reference permits physical
deletion. The
post-verdict sweep removes only quarantine sources already represented by its
cleanup ledger. Both use persisted due times and bounded exponential backoff so
broker, worker, or storage outages cannot create an in-memory-only retry tree
or starve later work. Their append-only audit details contain opaque
reservation/record IDs and evidence size/digest, never object keys, filenames,
addresses, message content, or other requester PII.

For versioned buckets, cleanup physically deletes and verifies absence of every
exact-key version and delete marker; for unversioned buckets it deletes and
verifies the exact current object is absent. The object-store identity therefore
requires bucket-versioning inspection, exact-key version listing, head,
ordinary delete, and delete-version permissions. Attachment quarantine and
application-verified orphan cleanup must remain deletable; if a version cannot
be removed, cleanup remains visibly pending and retries rather than reporting
deletion or releasing a file.

Adopted raw RFC822 is retained legal evidence and must never be
lifecycle-expired. For raw messages, only application-verified unadopted
reservation generations are purgeable. Adopted and unadopted raw objects use
the shared `quarantine/correspondence/raw/` prefix, so prefix-wide object lock
cannot distinguish adopted evidence from unadopted generations and would block
required orphan cleanup. Never add a lifecycle expiration to that prefix.
Govern raw-message retention from the durable receipt/adoption evidence, and
allow only the application's reference-checked cleanup to delete an unadopted
raw generation. A future requirement for object-locked raw evidence needs a
separate retained prefix or promotion design; it must not be approximated with
a blanket rule on this shared prefix. Pending/error scan rows remain
unavailable, and neither recovery sweep can release a file.

Responsive records should normally be delivered through secure application
links. An email-attachment feature must not become an alternate path around
`RecordItem`, redaction, exemption, installment, or authorization controls.

## Authorities

| Principal | Allowed correspondence responsibility |
|---|---|
| Records Officer | Legal drafting, adequate-search attestation, approval, queueing, matching/rematching, explicit clarification-response association and resolution, administrative terminal closure with a substantive reason, and restricted actions. |
| Ordinary authorized staff | Read correspondence for requests they can access and perform explicitly delegated non-legal drafting work. |
| Application Admin | Configure the application and inspect permitted operational state; this role alone cannot approve legal correspondence. |
| Attributed staff agent | Draft and preview for requests permitted by the mapped staff role; use registered REST primitives according to direct, human-confirmation, and human-only policy. |
| System outbound identity | Non-login Celery principal with exactly the permission to claim and report outbound deliveries; no token. |
| System inbound identity | Non-login Celery principal with exactly the permission to submit original Gmail RFC822 evidence; no token. |
| MCP identity | Read-only staff API subset; no correspondence mutations. |

Correspondence approval/queueing, clarification-response association,
clarification resolution, estimate-revision approval and queueing, and camera
exclusions remain explicit human-only handoffs for token callers. An
attributed staff agent may prepare an estimate-revision draft with a
substantive reason but cannot approve or queue it. A denial draft is
preparatory until an interactive Records Officer approves and queues it, and
only confirmed delivery applies denied status. Administrative terminal
closure requires Records Officer authority and a substantive reason. There is
no credential or alternate endpoint that bypasses those gates.

## Delivery sequence

The implementation is intentionally split into independently reviewed pull
requests: models and constraints; rendering/services; staff REST and
capabilities; staff UI; in-process outbound and inbound Gmail transport; inbound MIME/matching; email
cutover and operations; then final security and documentation regression.
Requester-facing delivery is now durable-only; the final regression gate must
keep the synchronous requester-mail paths and request-level estimate mutation
action absent.
